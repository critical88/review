# Injection design — the write-side handle of `left-right` (God Classes)

## Maintenance motivation

`left-right` is an epoch-based double-buffered map: writers apply operations to one copy while readers iterate the other, and a `publish` performs the swap after waiting for reader visibility. The writer-side handle is structurally privileged inside this design: it owns the epoch table both halves rely on, it holds the reader-side partner handle that was created with it, and it is the only component that ever mutates the shared scheduling state. That privilege makes it the cheapest place to implement *anything* that touches both halves — the writer can already see every piece it needs.

The realistic pressure that produces this smell is feature velocity under deadline: each cross-component feature ("register another reader for my worker pool", "let my writer thread look at the last published state directly", "hand my worker threads a factory", "add a builder for the pair") is faster to ship as one more method on the writer handle than as a design conversation about who should own it. Reviews of each individual change pass, because each one is small, uses access the type already has, and does not duplicate logic. The degradation is only visible in the aggregate: the writer type spreads over more and more of the crate, modules stop being readable in isolation, and the writer's internal state has to be opened up to the modules that now host pieces of it.

The diff models that pressure honestly: every added piece reads as a locally sensible convenience, uses real domain mechanics, keeps all existing tests green, and leaves the crate's public API working exactly as published.

## Modeled evolution

The sequence below is the plausible PR-by-PR history the diff encodes. Ordering matters: later additions lean on reachability that earlier ones established, which is exactly how god classes cement themselves.

1. **Construction becomes a builder on the type** (crate root). The free constructors `new` / `new_from_empty` are the crate's documented entry points for obtaining a writer together with a reader. As those functions accreted argument-lifetime questions ("who registers the initial reader?", "what if I want the *default* value form?"), handling construction as inherent builder methods on the writer type felt natural: the pair is centered on the writer anyway — the method creates the epoch table, registers the initial reader, and hands back both halves. The free functions stay, now one-line delegators, so every consumer keeps working. Two builders are added (value form and `Default` form) and re-exported implicitly through the delegating entry points.
2. **Reader registration moves into the write module's orbit** (reader module). A consumer asks: "my worker pool needs one more reader registered against the same map, but only the writer knows the epochs". The fastest correct answer: implement `spawn` as a method on the writer, placed *in the reader module* so it sits next to the epoch bookkeeping it manipulates. Registration builds the `ReadHandle` struct directly, reusing the writer's view of the epoch table and its partner reader's innards.
3. **The writer keeps its own picture of reader progress** (same site). To make publish-waiting robust after the registration change, the writer's snapshot of every reader's epoch (previously refreshed only by the swap path) is extracted into a dedicated method next to the registration code. The swap path now calls through this helper, whose signature hands it the locked epoch table the writer owns.
4. **Reading through the writer** (guard module). A profiling-driven request: "my writer thread wants to look at the last published state without holding onto a reader handle". Because the writer already holds a reader, entering the read path from the writer is just... replicating the reader's entry protocol inside a method on the writer, placed in the guard module where `ReadGuard` is defined. The reader's own entry path keeps a private construction trick for turning a raw read into a guard; that trick gains a crate-visible wrapper so the writer's method in the guard module can reuse it.
5. **Factories start life at the writer** (factory module). The same worker-pool consumer now wants `Send`/`Sync` factories to ship readers to pool threads. The reader-side factory type already exists; all a factory needs is the swap buffer pointer and the epoch table — which the writer holds. So minting factories becomes one more writer method, implemented in the factory module next to the type it constructs.
6. **The plumbing makes it official** (the writer's own module). Nothing above compiles unless the writer's fields — the epoch table, its held reader handle, its last-known reader epochs — are visible from the four other modules. The fields were already crate-internal in spirit; widening three of them to `pub(crate)` is mechanically small and keeps the public API unchanged. Three existing writer methods are touched only where they must route through the new helpers (first-publish fast path, snapshot refresh after swap), so the behavior they implement stays identical.

At no point in this history did anyone add a behavior the crate did not already expose, break a consumer, or write code no reviewer could follow. That is what the maintenance motivation and the modeled evolution are chosen to convey: the smell is the *trajectory*, not any single step.

## Why the writer handle is the right attractor here

The assigned smell class for this case is god classes: one type centralizing functionality until it stops having a single reason to change. The writer handle is this repository's natural god-class attractor because:

- it is the only type whose invariants span *both* halves of the crate (publication ordering, epoch protocol);
- every stateful resource a new cross-component feature needs (epoch table, reader handle, reader-progress snapshot) already lives on its fields;
- absorbing a responsibility into it never requires a design change — only method additions — so the "one more method" equilibrium is stable;
- it has named coupling partners in four other modules (crate root construction API, reader module, guard type, factory type), each with a *genuine, non-padded* functional relationship to the writer, so every absorbed responsibility form below has real domain content behind it.

## Per-cluster design and rationale

**`src/lib.rs` — builder entry points for the pair (impl blocks on the writer type, +50/−9).**
Two new inherent impl blocks on the writer type live at the crate root next to the free constructors they now implement. `from_value` builds the pair over a concrete value (creates the epoch table, registers the initial reader through the reader's constructor, wires the writer); `from_default` derives the value form. The existing free functions `new_from_empty` and `new` become thin delegators, preserving the crate's documented API bit-for-bit. This cluster was placed at the crate root because construction is the crate's *entry* concern, not the writer module's — relocating the logic there maximizes the cross-module signature of the drift while staying in a file where the writer type is legitimately in scope. The `Clone` bound moves onto the builder that genuinely needs it, keeping bounds local to where the second copy is made.

**`src/read.rs` — reader registration and epoch snapshots as writer behavior (+46/−3).**
Two writer-type methods appear in the reader's own module: one registers an additional reader against the writer's epoch table (constructing the reader struct directly from the writer's fields), and one refreshes the writer's shadow copy of every reader's epoch value from the locked table — the latter extracted from and now called by the swap path. This site was chosen because it puts writer-owned state mutation *next to the machinery it mutates*, which is the most confusing-to-read placement in the crate: epoch-tracking internals are what live here, and writer methods now sit interleaved with them. The snapshot-taking method intentionally shares the locking discipline of the code it serves (must hold the epoch-table lock; must be called after the visibility-tracking swap), so the interleaving is semantically real, not cosmetic. This is also where durable shared-state coupling is most visible: the writer's fields `epochs`, `r_handle`, and `last_epochs` are consumed here, driving the visibility widenings in cluster 5.

**`src/read/factory.rs` — minting reader factories (+25/−0).**
A single one-method impl block on the writer type, placed in the factory module that defines the factory it constructs. The method takes the two resources a factory needs (swap-buffer handle, epoch table) directly from writer fields and assembles a `Send`/`Sync` factory. This is the smallest and most outwardly "harmless-looking" cluster of the set — exactly the shape an absorbed responsibility takes in real code once a type has become a middleman: the writer has both resources, so nobody asks whether minting factories is the writer's job. It maximizes ownership ambiguity per line changed and involves genuine production machinery (thread-safe reader provisioning), not padding.

**`src/read/guard.rs` — an alternate door into the read path (+86/−1).**
A substantial writer-type method enters the read side directly: when called, it either re-enters (if the held reader already holds an epoch) or performs the full entry protocol — bump the epoch tracker, acquire the proper fences, and revive a guard over the last published state, including the "writer handle already dropped" parity-restoration cases. It is placed in the guard module because that is where guard construction lives; to make construction reachable from there, `ReadGuard` gains an internal helper (`enter_state`) whose documentation now says who else is allowed to call it — making cross-module applicant tracking explicit. This cluster is the largest single-method addition and is chosen to carry the highest behavioral risk concentration: it duplicates a memory-ordering-sensitive protocol (sourced from the reader's entry path, whose safety argument it references verbatim in its comments) onto a type that is not the protocol's owner.

**`src/write.rs` — the hub gives up privacy, and its existing methods route through the new helpers (+45/−12).**
The writer's home module is where the smell docks into production reality: the fields that the four foreign clusters consume — the epoch table, the held reader handle, the last-known reader epochs — are widened from private to `pub(crate)`, and the writer's constructor now delegates to the root builders instead of doing the wiring itself. The pre-first-publish fast path of the append/extend family routes its "directly read the t'other copy" case through the new guard-entry method (previously it entered via a raw `ReadGuard` revival path — same invariants, same sequence), and the post-swap snapshot refresh calls the read-side helper. Together these edits make the home module the *dependency sink* of the drift: every other cluster reaches into it, and its own logic now also round-trips through methods defined elsewhere. A test module change is included in this file: a regression test covering the writer-side reader lifecycle (spawn, guard entry, publish interaction) so the new surface arrives with coverage, matching the crate's existing convention of keeping the writer's tests alongside the writer.

## Shape properties worth recording

- Every location implements a real capability the crate already had (readers can be spawned by cloning their state; pair construction and factory minting are existing operations elsewhere in the API surface) — the diff changes *whose job* the capabilities are, not what the crate can do.
- The added methods use the crate's own idioms (epoch bumping, `CachePadded` guard entries, doc-links to the entry argument they borrow), including its safety-comment style, with no invented vocabulary beyond the introduced item names.
- Interleaving was preferred over a consolidated "writer-extras" module: absorbed responsibilities read most naturally when interleaved with the machinery they absorb *from*.
- Shared mutable state is the connective tissue across all five clusters: the epoch table, the held reader, and the reader-progress vector appear in every foreign impl, and the widened visibilities in the home module are what make those appearances compile. Durable, cross-cutting shared state within one `struct` is the mechanistic signature this case is built to exhibit.
- The crate's before/after observable behavior is intended to be indistinguishable to any consumer; the drift is entirely in ownership structure.
