# Injection design record — scattered template-convention wiring (`smellgen-actions-starter-workflo__5QuxB7F`)

## Repository context

`actions/starter-workflows` ships a validation sweep (`script/validate-data/index.ts`, run in CI over every starter workflow in `ci/`, `automation/`, `code-scanning/`, `pages/`, `deployments/`) and a GHES sync (`script/sync-ghes/index.ts`) that decides which starter workflows are compatible with GitHub Enterprise Server and rebuilds the `ghes` branch from that decision. The two scripts are separate npm projects, each with its own `package.json`, `tsconfig.json` (including only `*.ts` in its own directory), and a `settings.json` that configures folders, categories/partners, and sync behavior.

Both scripts are built around the same domain knowledge — the *starter-template conventions*: where a workflow keeps its `properties/*.properties.json` companion data, how the `iconName` field in that data distinguishes embedded `octicon <name>` references from plain svg-file names under the repository `icons/` folder, the special status of `blank.yml` templates, the role of template folders such as `deployments` and `code-scanning`, and which creators mark a partner template for GHES purposes. In the clean revision each script holds this knowledge inline as short expressions; the properties-path expression, the icon classification, and the folder/creator gates existed twice, once per script, in slightly different shapes (the validation regex `/^octicon\s+/` versus the sync's `startsWith("octicon")` prefix test being the clearest historic drift).

## Modeled evolution and motivation

The diff models a plausible mid-migration state that real repositories fall into constantly:

1. **Motivation to share.** Both scripts had drifted into maintaining their own copies of the template conventions. A change to the properties layout or icon rules required remembering two scripts, and the two icon flavors had already diverged once. A maintainer starts extracting the conventions into a shared rule layer so that validate-data and sync-ghes reuse one implementation instead of two.

2. **First extraction lands in the validation project.** The natural first home is `script/validate-data`, where the convention checks are densest. The migration scaffolding chooses a string-keyed registry: modules *register* named rule implementations at import time, and consumers *resolve* those names at runtime. Why a name table rather than plain imports? Because the registry also offers per-script configuration — each script's `settings.json` maps consumer-facing slot names to registered rule names, so which implementation runs can be tuned per script without code changes. That kind of configurability is a common, believable justification at the start of such a refactor.

3. **Topical modules hold the first fragments.** The properties/workflow path conventions move into one topical module (`templatePaths.ts`), the icon conventions into another (`templateIcons.ts`). Each module defines its helpers and registers them with stable string names as an import side effect.

4. **Migration stalls part-way through the validation script itself.** The entry script converts its inline conventions to registry lookups, but the last two conventions — the `blank.yml` exemption and the `deployments` creator requirement — are contributed as small local functions inside `index.ts` that register themselves, rather than moving into the topical module. A stalled migration rarely moves everything at once; leaving the last extracts in place is what a partially-completed commit series looks like.

5. **The GHES script adopts the registry from its sibling project** — partially. Because the two scripts are independent npm projects with `*.ts`-only include scopes, the lowest-friction adoption is to import the validation project's rule modules (for their registration side effects) and add the sync's own slot map to its own `settings.json`. The sync gets the properties-path and icon rules this way, but its two other conventions (partner-creator classification, code-scanning eligibility) are likewise contributed as local functions inside its `index.ts` rather than moving anywhere.

The end state is the classic shotgun-surgery production condition: one conceptual convention change (say, relocating local svg icon storage) touches a topical module, possibly an entry-script local, *both* settings files, and requires the reader to trace slot name → rule name → implementation across script boundaries just to find which code runs.

## Overall design of the injected change

- A registry core lives in `script/validate-data/templateRules.ts`: a `TemplateRule` interface, a name-keyed table, `registerTemplateRule(name, impl)` as the registration call site, and `templateRuleFor(name)` as the resolver that throws a named-missing error when a lookup fails.
- Convention implementations live in two new topical modules in the validation project (`templatePaths.ts`, `templateIcons.ts`), each purely a source of registered fragments plus its own imports.
- Each entry script consumes conventions through two added lookups: read the `templateRules` slot map from its own `settings.json`, then call `templateRuleFor(templateRules["<slot>"])` with the consumer's arguments. The validation script threads a `templateRules` parameter through `checkWorkflows`/`checkWorkflow`; the sync reads its map once in `main()` and closes over it.
- Each entry script additionally defines two small local convention fragments and registers them at module scope, so fragments originate from four distinct files in three different roles (topical module, validation entry, sync entry).
- The icon conventions deliberately keep both historic flavors: the validation-oriented fragment classifies an embedded reference with the whitespace-anchored form, while a GHES-oriented fragment answers the "is this an embedded icon" question with a prefix test, preserving each script's observable decisions instead of unifying semantics mid-migration.

## Deliberate structural variation

The fragments were not all injected in one uniform shape, because real stalled migrations are not uniform:

- **Homes vary**: four fragments live in dedicated topical modules, four live inside the entry scripts as local functions, and the registry core itself is a third kind of home. A consolidation obligation therefore cannot be located by pattern-matching on a single file arrangement alone.
- **Registration names vary in taxonomy**: dotted names (`icons.ref.octicon-prefix`), flat names (`partners.creator.match`), and slot keys (`properties-path`) that do not lexically match the registered names they select, so no single string search reveals the full wiring.
- **Argument shapes vary**: path fragments take `(folder, name)`, the validation octicon-name extract takes the raw reference and returns a match array, the GHES embedded-icon fragment takes `iconName` and returns a boolean, and the folder fragments take a path. Consumers therefore differ in how much wrapping logic they retain locally.
- **Selection is split between code and config**: both settings files carry slot maps, but the entry scripts resolve them through different threading styles (an explicit parameter through two functions in validate-data versus a closed-over map in sync-ghes).
- **Both icon flavors kept deliberately**: unifying them would have changed observable validation semantics (the whitespace-anchored test doubling as an extraction regex), and a migration whose purpose is sharing implementations would not silently alter probe behavior, so the module carries both variants with a comment documenting the intent.

## Behavior preservation

Every injected transformation is behavior-preserving on the repository's own data while it is running: the validation sweep still reports the same errors over the whole catalogue, and the GHES compatibility decisions and file lists are unchanged, including for icons — the corpus's 184 `iconName` values are either plain svg-name slugs or well-formed `octicon <name>` references, so the two icon flavors classify every actual template identically. The two flavors differ only on inputs the corpus does not contain (for example a value beginning with `octicon` and no separator-space-plus-name, or `not-octicon` spellings), which is exactly the kind of latent divergence such partially-shared convention code accumulates in production.
