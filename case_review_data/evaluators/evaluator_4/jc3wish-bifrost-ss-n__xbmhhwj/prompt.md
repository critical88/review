# Destination name handling for output plugins needs one home

Our connector's output plugins write to a lot of different systems: brokers, caches, document stores, a search engine. On most of them the target name itself is not a static string — people configure it as a `{$...}` reference that we fill in with values from the event at runtime. The topic they produce to, the exchange / routing key / queue they publish against, the cache key, the index, the database and collection, the ActiveMQ destination: any of these can be built from business data that we did not choose.

We have been paying for that flexibility little by little. Every time one of these systems rejected or mangled a name that a business value produced, the fix went in wherever the incident was: one destination got a character whitelist, another got a replacement table and a 255-byte cap, a third got a hand-written byte scrub and a fallback name for the empty case, a fourth got a regexp filter and a 250-byte cap, one plugin ended up with the same `$`-replacement and empty-name fallback pasted into both its write path and its delete path, the search plugin grew a lowercase-plus-replacement rule around the index name it was already lowercasing, and the STOMP destination got its own rune-by-rune scrub with a `Bifrost_`-prefixed fallback. Each of those is a small block sitting right next to the code that resolves the `{$...}` template, each with its own comment explaining why it exists.

These fixes work individually, but the situation is wearing us down:

- we are about to onboard two more destinations and do not want to research and hand-roll this yet another time;
- when a rule changes — a newly forbidden character, a different length limit, a different empty-name policy for one system — we have to find and touch each plugin separately, and the copies are deliberately written in different styles, so there is no reliable way to grep for all of them; we already nearly missed one plugin last time this came up;
- the shared plugin binding package that every destination imports has the template resolution helper, but nobody can point to any place in this codebase and say "these are our destination naming rules".

Please rework this while we are near it. We want the naming policy to have one home: a single shared, documented mechanism in the package all the destination plugins already depend on, where each destination states its own rules — which characters it cannot take and what to replace them with, how long a name it accepts, whether it wants the name lowercased, and which fallback name to use when the resolved value comes out empty — and gets its names prepared in one uniform way.

This must be behavior-preserving, since live pipelines depend on the exact names being written today: for the same event and configuration, each destination must end up with exactly the name it gets now — same characters replaced, same caps applied, same case handling, same fallbacks, same template resolution semantics. Existing saved plugin configurations must keep working as-is, the wire behavior of every destination must not change, and anything that resolves `{$...}` references for row *values* (the column mapping in the MySQL and ClickHouse paths, message payloads, cache values) is a different topic and should stay as it is.

A good outcome looks like: one shared place where all the per-destination naming rules are declared and applied; each plugin stating its rules (or reusing another destination's) instead of containing its own implementation; adding a naming rule for a future destination touching only that destination and the shared place; and the codebase still building with its tests passing.
